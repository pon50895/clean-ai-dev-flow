# grill-me — 動工前逼問式訪談

改造自 mattpocock/skills 的 `grill-me` + `grilling`(MIT license),接上本專案 GSD 四階段的 **Discuss** 關卡。單一職責:在動手前,用一次一題的訪談把需求與決策釘死。不寫 code、不改檔,只問。

## 何時用

- 任何「新功能 / 修 Bug / 重構」進 Plan 之前(GSD Discuss)。
- 需求模糊、規格可能互相矛盾、或你正想憑假設開工時——這是 R2(禁腦補需求)的防線。
- 使用者說「這個 plan 對嗎 / 有沒有漏 / 幫我想清楚」。

## 規則(逐條照做)

1. **一次只問一題**,等回答再問下一題。一次丟一堆問題會讓人無從答起。
2. **走決策樹**:順著這個決策的每個分支往下,逐一解決分支間的依賴。先問上游決策,再問被它決定的下游。
3. **每題都附你的推薦答案**——不是空問,是「我建議 X,因為 Y,你同意嗎?」讓使用者用最小力氣拍板或推翻。
4. **事實自己查、決策才問人**:能從環境(檔案、codebase-memory、git、既有 spec)查到的事實,自己去查,不要拿來問。只有**決策**(取捨、優先序、範圍)才交給使用者。
5. **達成共識前不動手**:不寫 code、不開 PR、不改檔,直到使用者確認「我們理解一致了」。

## 該問什麼(命理平台脈絡)

- **範圍**:這次要做什麼、不做什麼?哪些是 YAGNI 可砍?
- **驗收條件**:怎樣算完成?哪條 E2E / 哪個 200 / 哪個視覺對照能證明?
- **既有衝突**:規格文件互相矛盾嗎?某模組是否已有其他 worktree 佔用(看 `.planning/HANDOFF/`)?
- **定位 / 法遵**(碰對外文案 / 金流 / 命理解讀時):賦權非恐嚇?供應商保密?有沒有宣稱未發生的驗證?
- **風險假設**:哪個假設錯了會讓整件事白做?先驗那個。

## 收尾

達成共識後,產出一段「共識摘要」(要做什麼 / 不做什麼 / 驗收條件 / 已拍板的決策),交給下一步:寫進 `.planning/phases/<phase>/PLAN.md` 進 Plan 階段。需求牽涉領域模型 / 術語 / schema 時,改用 `grill-with-docs`(訪談同時把術語與決策寫進文件)。
