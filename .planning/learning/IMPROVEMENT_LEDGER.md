# 改進 Ledger

> **這是範本。** 第一次跑週循環時,把下方範例節換成你的實際資料。
>
> **單一滾動檔,不產 dated 報告。** 每輪追加一節在最上面。超過 200 行把最舊的節搬 `.planning/archive/`。
> (dated 報告 = 前幾次檢討蒸發的那種東西 —— 產出時很有成就感,三天後沒人記得它存在。)
>
> **觸發**:`session-learning-inject.sh`(SessionStart hook)讀本檔最後日期,>7 天就在開場印過期提醒。
> **不排無人值守 cron** —— step 4 的 validation gate 要人在場逐筆裁決;
> cron 在人不在時跑 = 產出一份沒人裁決的報告 = 同一個死法再來一次。
>
> **完整流程**:`.claude/skills/skillopt/SKILL.md`(step 0-8)

## 為什麼需要這個檔

**寫規則不改變行為。** 一個真實案例的三次「檢討 → 寫規則 → 下次照犯」:

| | |
|---|---|
| 第一次檢討提 5 項 | **落地 2 項,兩項都是機器 gate** |
| 另外 3 項是 prose | **至今沒寫進任何目標檔**,而**沒有任何東西會發現** |
| 兩天後 | 同一個人漏寫其中一條 → agent 跑 `rm` → 使用者被彈窗 |
| 兩個月前 | 一份 handoff 就診斷過「學習迴圈沒 consumer」→ **那個診斷同樣沒有 consumer** |

**斷掉的環節不是「想不到要改什麼」,是「提案落地與生效沒人驗收」。**

所以這個檔的核心不是記錄提案,是**讓下一輪的 step 0 有東西可驗**。
提案桌的 `狀態` 欄就是驗收清單。

## 系統自身的死亡判據

**在你建立這個檔的當天,就把三個月後的檢查日期和判據寫死在這裡。**
不要等三個月後再定義「什麼算成功」—— 那時候你會為了讓它看起來成功而挑指標。

範例(照你的情境改):

| # | 判據 | 檢查日 |
|---|---|---|
| 1 | A(被推翻判定數)週均沒有從 `<基準>` 降到 `<目標>` | YYYY-MM-DD |
| 2 | `gate-fires.jsonl` 有活動,但 `violations.jsonl` 連續 30 天零新增 ← producer 邊死了 | 同上 |
| 3 | 本 ledger 斷更 ≥3 週 | 同上 |

**三條都必須是檔案裡的數字,不是感覺。** 任何人都能查,包括三個月後的你自己 ——
尤其是三個月後的你自己,因為那時候你會想相信它有用。
